What it shows

  1. Accuracy shows no dependence on engine, kpool fixes, draft depth or weights here: every configuration lands at 84.7-86.9%, and every per-question comparison of first passes is consistent with noise (sign-test p ≥ 0.23).
  2. Finishing long reasoning depends on the engine. On the same 3.25bpw weights, tpurtell 0.7.0 left 6 of 594 GPQA answers empty against 20 for tpurtell 0.8.0, about a third as many (Fisher p = 0.009); on the hard-question screen it failed about half as often (12 vs 24 of 40 in the same session).
  3. The two kpool bugs are real but are not the main cause of the loops. The fixes, shipped in tpurtell 0.9.0, pass upstream's regression tests, at no measurable accuracy cost. Their expected benefit is in long-lived servers with prefix caching, which these fresh-server runs rarely exercise. No detectable completion cost either: on 4bpw, tpurtell 0.9.0 left 23 of 594 answers empty against 15 for tpurtell 0.8.0 with the same prompts (Fisher p = 0.25). Resampling questions, the difference is -3 to +19 answers, so a small cost is not excluded.
  4. Empty answers explain only part of the gap to published scores (NVIDIA 92.1, Red Hat 90.6): scoring only answered questions would add 0.9-3.4 points (86.4-88.7%), still below both. The rest mixes quantization, harness and other runtime effects, which these runs cannot separate.
