GLM-5.3-Flash on 2x RTX PRO 6000: end-to-end receipts

Accuracy, completion, speed and kernel-correctness measurements of locally served GLM-5.3-Flash EXL3 quants on tpurtell's vLLM-based engine releases and locally patched builds of them, under fixed, versioned protocols. Every number links to raw per-item receipts and can be recomputed with the repository's tools (what has no row-level receipt).

What it shows

  1. A decode masking path in tpurtell 0.8.0/0.9.0's DCP1 layout skipped the newest 1-3 tokens at causal lengths up to 2,043 that are not a multiple of 4 (supported: index check on the image's own kernels). The fix (tpurtell PR #6, released in 0.9.1) removes it, and decode then agrees much better with prefill below 2,044 tokens (KL 0.066 → 0.010; two runs of the 0.9.1 release give 0.006-0.008 on the same prompts). Its effect on answers is unmeasured. See the investigation. Evidence: index check · decode vs prefill
  2. The two upstream kpool bugs were present in the 0.7.0 and 0.8.0 images (supported); upstream's regression tests pass with the fixes (33/33, from 29/33). The 0.9.0 and 0.9.1 release images pass them too (tested 2026-10-09). Evidence: kernel tests
  3. tpurtell 0.7.0 as shipped left fewer GPQA questions unanswered than tpurtell 0.9.1 (3.25bpw, three passes each with their own request seeds): 4 vs 16 empty answers of 594, on 4 vs 11 questions (supported: question-clustered test p = 0.009). The question arose from pass 1; passes 2 and 3 alone point the same way (4 vs 11 empty answers on 1 vs 7 questions, p = 0.06). Accuracy does not differ measurably (88.2% vs 86.9%). 0.7.0 differs from 0.9.1 in several ways at once (draft depth, parallel layout, kernels, vision, KV pool), so the cause is open. Evidence: chart below · clustered comparisons
  4. 3.25bpw and 4bpw TR3 (Brandon) on tpurtell 0.9.1 show no measurable difference over three passes each: raw accuracy -1.2 points (-4.2 to +1.7), empty answers 16 vs 17 (descriptive). Evidence: chart below · clustered comparisons
  5. One pass does not separate configurations in accuracy (descriptive): passes of one configuration with their own request seeds differ by 0.5-3.5 points, about as much as pass 1 of all 10 configurations (84.3-87.9% raw, 85.4-89.4% by the audited stated answer); every question-paired pass-1 comparison is consistent with noise (McNemar p ≥ 0.45). No higher-precision reference was run on this hardware, so whether these quants cost accuracy is not measured here. Evidence: pass-to-pass spread · pass 1 of every configuration

Withdrawal notice (2026-10-09). Every repeat of the earlier hard-question screens (protocols v0 and v1, 2026-09-30 to 2026-10-08) sent request seed 1234. Batching made the repeats vary, but every repeat drew on the same sampler noise, so that variation was not statistically meaningful. Their failure rates and intervals, the layout-bisection statistics and the question-level observations drawn from them are withdrawn. Only repeat 1 of each question from each configuration's first screen is kept, as a single draw. The withdrawn rows remain in the git history. Details and evidence: the investigation.
