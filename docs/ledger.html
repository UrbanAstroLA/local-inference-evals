The questions

  1. Which weights and engine release to run on two RTX PRO 6000 GPUs: accuracy, completion, speed, KV capacity.
  2. Why some hard GPQA questions do not finish within the 327,680-token budget (investigation).
  3. Which factors besides the configuration move a result, and how to control them (CONFOUNDS.md).
  4. Why tpurtell 0.7.0 left fewer GPQA answers empty than 0.9.1 (investigation).

2026-10-11. Source audit, and which pool the 511-pool slice drops.

  • Kernel and DCP source audit (amendments 10-10a; CPU; three independent audits of the 0.7.0, 0.8.0 and 0.9.1 source): no defect unique to 0.9.1 in attention, the DCP combine, record readers, graphs or scratch. The known indexer write defects are 0.7.0's and 0.8.0's and fixed in 0.9.1. Common to every version: the top-k selects 512 compressed-key pools and the engine keeps output columns 0-510 to make room for the newest tokens. No top-k path sorts its output, so the discarded pool (the one in column 511) is not guaranteed to be the weakest. Upstream vLLM keeps all 512.
  • Correction: the looping investigation's code question 6 said these releases' top-k emits winners first, so the discarded pool would be among the lowest-scored. No top-k path sorts its output; a dated note on that question now points here (looping, open questions).
  • Stage 1 (each release's top-k kernels on frozen synthetic inputs; one GPU, no model; 0.10 GPU-hours): on 0.9.1's tiled route (5-8 requests in flight at 3 draft tokens) the discarded pool ranked better than 480 of 512 in 94-98% of rows at 1,024-16,384 pools; on the fused route (1-4 requests) 0-1%; on 0.7.0's path 3-21%.
  • Stage 2 (real serving inputs captured on 0.9.1 in eager mode, replayed through each release's kernels; 1.16 GPU-hours): 88.1% of 9,944 live tiled decode rows; fused 0.5%; 0.7.0's path on the identical bytes 6.9%. The route, which follows the number of requests in flight, alone decides it. Selected sets matched an fp64 reference.
  • Phase 3 (0.58 GPU-hours): switching the two-level fold off did not meet the criterion (the weakest pool in column 511 in 39.8% of tiled rows); moving the lowest-scoring selected pool into column 511 did, in 100% of rows offline and in place, with the selected set unchanged. This is a correction to the engine's 511-pool selection policy, not a restoration of upstream's 512-pool policy.

2026-10-11. The kpool tail ring.

  • In stage 2's second capture, 16 index-K pools were byte-identical across two different requests, some decoding as NaN. A CPU forensic pass found raw indexer key and gate rows for tail-ring slots 4-7, written into blocks then owned by other requests (amendment 10d).
  • Cause (amendment 10e; CPU trace with the real kernels): this build builds attention metadata without token positions, which upstream vLLM has passed since GLM-5.3-Flash support landed. Without them, every tail write from position 8 goes to a shared null block, and through stale ids left by the runner's start-up warm-up, occasionally into another request's blocks. The same omission is in 0.7.0's source. Amendment 10d had nominated a stale request row or a block-table staging race; no staging race was found (25,000 steps against a CPU shadow).
  • Verification (amendment 10f; 1.16 GPU-hours): unmodified 0.9.1 in its shipped graph mode sent 98% of tail writes to the null block on each rank, and 6 into live attention blocks. With positions passed and a graph-safe write: 0 and 0; 104 of 104 requests completed; throughput unchanged.
  • A CPU harness running each release's real kernels: 0.7.0 gets 100% of decode-completed pools wrong at 1, 2 and 8 requests in flight; 0.9.1 0% at 1, 47-57% at 2 and 78-90% at 8. 0.7.0 is the more affected engine; that does not exclude a role in its better completion, which is untested (corrected; see 2026-10-11, late). The investigation's total: 17.11 GPU-hours.
