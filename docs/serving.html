Speed, acceptance and KV capacity

3.25bpw weights, 16 fixed GPQA prompts, 4,096 tokens, temperature 1.0, one run per configuration: tpurtell 0.8.0 with and without the kpool fixes (2026-10-04), and tpurtell 0.9.0 with and without the DCP1 tail fix (2026-10-08; see the looping investigation). The kpool fixes show no consistent change: with the same speculation setting, decode speed and throughput move by -7% to +3% and acceptance by at most 0.004 (see the comparison).

What it shows

  1. KV capacity depends on the layout; tpurtell's default DCP1 layout with MLA layer ownership holds the most (supported: reported by the server at start-up, same memory setting). Evidence: KV table
  2. Neither fix shows a speed cost, in single runs (descriptive; one run per configuration, no noise floor). Evidence: decode speed · throughput · acceptance
  3. The engine is not bitwise reproducible, even one request at a time (supported): the same configuration run twice with greedy decoding diverges after a median of 318 characters. Evidence: greedy agreement
Single runs, no noise floor. Every speed and acceptance figure on this page comes from one run per configuration; no configuration was repeated, so differences of a few percent cannot be told from run-to-run variation.
