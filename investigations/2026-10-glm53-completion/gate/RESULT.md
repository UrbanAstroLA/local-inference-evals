## Prefill-branch finding: affected, narrowly

**From source.** The indexer decides decode vs prefill with its own split (`indexer.py` `split_decodes_and_prefills`,
decode_threshold 4). `use_flattening=True` (from the log), so `require_uniform` is False. The runner sorts each batch
decode-first (`model_runner.py` `sort_batch_req_ids`).

- Decode rows in mixed batches therefore go through the indexer's **decode** branch (B12x, corrected).
- Report-dispatch's "mixed batches send decode rows through extend" applies to the sparse MLA attention backend, not
  to indexer selection.
- Only rows with more than 4 query tokens use the prefill branch.
- The DeepGEMM decode fallback needs `requires_padding`, which flattening never sets.

**Offline (release kernel, one GPU, `offline/prefill_topk.jsonl`).** The compiled `top_k_per_row_prefill` returns ids
relative to the row start (all 768 test rows).

| row length | column 511 |
|---|---|
| more than 512 candidates | lowest, or an exact tie, in 100% of 128 synthetic rows (4 distributions incl. plateaus and zero ties) and 576/576 real-score rows |
| exactly 512 candidates | the rows come back in index order, so column 511 = pool 511, the newest complete pool, regardless of score (16/16; not lowest in 16/16) |
| fewer than 512 | column 511 = -1 |

In serving this hits the 4 prefill rows at positions 2048-2051 of every prefill that starts below 2048.

**In situ (pre-correction, prefill branch).**

- 2,200 of 14.85 M clean full rows had a non-lowest pool in column 511. In all of them at least 32 selected pools scored
  below it.
- That is 1,200 on rank 0 = 50 prefills × 4 rows × 6 layers, and 1,000 on rank 1 = 50 × 4 × 5. This matches the
  exactly-512 rows **(inferred from the counts)**.

**Fix.** Gather the selected scores from the logits the prefill top-k ranked, then apply the same move. DCP1 only.

## Checker design (`check/col511check.py`)

**Hooks.** It is called in `sparse_attn_indexer_kpool` at three points on each branch:

- before the correction: snapshot of ids and scores;
- after the correction;
- after the expanded token buffer is written: consumer check.

**Device side.** All device work is fixed-shape torch ops into checker-owned buffers: no `.item()`, no boolean-mask
indexing, no host-to-device copies. It is graph-capturable; one scalar `setitem` that copied host-to-device was found
and fixed in the offline smoke.

- Counters are keyed by graph mode (eager / piecewise / FULL / capture-phase warm-up) × branch (decode-fused,
  decode-tiled, prefill) × rows (0-64, >64) × mixed.
- Records of failing rows are bounded.
- A per-step route ring covers one DSA layer per rank.

**Readout.** A background thread copies the buffers on a private stream into pinned memory, on DUMP triggers, never
inside a capture.

**Host side, observe-only wrappers.**

- Python-executed calls, by mode and whether capturing.
- Runner FULL replays and piecewise runs, by token count.
- Buffers are allocated at BlockTables init, before capture.

**Checks.**

- **pre.** Rank of the column-511 pool among the valid selected (kernel scores): lowest / tie / not lowest, with
  below-counts 1-3, 4-31 and ≥32. Unfilled rows with a valid pool in column 511.
- **(a)** Sorted-id equality, before vs after.
- **(b)** Column 511 = minimum kernel score; ties counted.
- **(c)** Unfilled rows (fewer than 512 valid): column 511 must be −1. Also: −1 slots must score −inf, valid count must
  equal min(n, 512), ids must be in range.
- **(d)** Ties.
- **(e)** NaN/inf kernel-score rows, excluded from (b).
- **(f)**
  - Consumer check: the expanded buffer the attention reads equals the corrected pools[:511] (count and token-id sum)
    plus the tail.
  - Stale-digest check per layer/branch: identical consecutive kernel-output digests are flagged.
  - Pool count vs `dec_seq//4`.
- **Independent check.** Two valid rows per call are re-scored in fp64 from the cache page bytes (decode) or the
  gathered index-K workspace (prefill). Column 511 must be lowest within the documented fp32 bound
  (Σ|q·k|·|w|·scale·162·2⁻²⁴), pre and post. The kernel score must lie within the bound.

**Offline validation (GPU0, `offline/checker_gpu_smoke_c.jsonl`): 12/12 pass.**

- Negative controls (no fix, set corruption, stale consumer buffer, repeated inputs, NaN row) are all detected.
- Zero host syncs under `torch.cuda.set_sync_debug_mode("error")`.
- Pre + fix + post + expand + consumer captured in a CUDA graph and replayed on fresh data equals eager. Stale replay
  is flagged.
- The real samplers match the phase-2 fp64 reference on stored capture bytes exactly (max diff 0.0), and also run
  inside a captured graph.

### Corrupted / NaN pools (condition 3; not repaired by the correction)

The fp64 re-score of sampled rows found at least one *selected* pool whose stored bytes decode to NaN in:

| | decode | prefill |
|---|---|---|
| rank 0 | 2,398 of 30,300 sampled rows (7.9%) | 350 of 8,862 (3.9%) |
| rank 1 | 8,211 of 25,250 (32.5%) | 1,480 of 7,385 (20.0%) |

Kernel scores in those rows were finite: kernel NaN/inf rows = 0. **(inferred)** The kernel's ReLU (max with 0) maps NaN
dots to 0. These rows are excluded from the fp64 criterion. On kernel scores they still pass (a)-(c).

**(inferred)** These are the tail-ring corruption family of amendments 10d/10e: raw bf16 tail rows written into indexer
pages, mainly on rank 1, persisting in prefix-cached blocks. That fix is excluded from this build by design. A negative
completion result from the GPQA arm therefore cannot exclude effects of this defect.

## Not covered / limitations

- **Prefill at DCP>1:** not corrected (the indices after the merge are not local-logit offsets). The decode part at
  DCP>1 was not tested. Neither is the shipped configuration.
- **Piecewise graphs:** only 66 calls, all with short-context unfilled rows. The indexer runs eagerly at piecewise
  replay (eager-break op, `sparse_attn_indexer_kpool.py:258`), the same code as the eager path that was measured
  heavily.
- **Candidate image:** not started on its own (the check image differs only by guarded additions).
- **Selected set vs a global fp64 top-512:** not re-measured in this run. Phase 3 did this, offline and in place. Here
  the set is checked as preserved across the correction, and the kernel scores are checked against fp64 for the
  selected pools.
- **Completion and accuracy effects:** not addressed (amendment 11, completion arm).
