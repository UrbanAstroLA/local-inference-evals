# hard-prompt-screen / v1

A fast screen for non-completion (loops and exhaustion) on long reasoning, used to rank configurations before
spending a full GPQA run. It ranks; it does not estimate population rates.

**Items:** GPQA Diamond doc ids 79, 13, 127, 88, 121 under `gpqa-diamond/v1` prompt rendering (every one produced an
empty answer in earlier full runs), 8 repeats each = 40 requests. Prompts are the lm-eval-rendered chat messages;
`prompt_hash` is recorded so the exact prompt can be verified.
**Sampling:** temperature 1.0, top_p 0.95, `seed` 1234 on every request, max_tokens 327,680, thinking on, streaming.
**Schedule:** 8 concurrent, order fixed by `random.Random(7).shuffle` over (doc, repeat) pairs.
**Early stop:** from 30,000 reasoning characters, every 10,000 new characters, compute the zlib compression ratio of
the last 30,000 characters; three consecutive values below 0.10 close the stream (class `loop`). Validated offline
on 80 earlier traces: stopped 27/28 loops, 0/44 completions, 0/8 exhaustions.
**Classes:** `ok` = finish reason `stop`; `loop` = stopped early, or finish `length` with tail zlib ratio < 0.15;
`exhaust` = finish `length` with ratio >= 0.15; `error` = transport or server error.
**Primary metric:** non-ok (loop + exhaust) out of 40. Decision rules are set per investigation, in advance.

**v0** (2026-09-30 runs) is identical except it has no early stop; classes agree on the validation set, but v0 and
v1 runs are not mixed in comparisons.

**Known limitations (recorded 2026-10-06).** (1) Items were selected from one engine's failures (empty answers in the tpurtell 0.8.0 GPQA runs), which biases
cross-engine comparisons toward the other engine; within-engine comparisons are unaffected. (2) The seed is fixed for
every repeat; repeats are independent in practice only because concurrent batching makes the engine nondeterministic
(observed: all repeats distinct, diverging within 0-266 characters). (3) Outcomes cluster by item, so `non_ok_ci95`
(Wilson, assumes independence) is too narrow. A future v2 should vary the seed per repeat, select items without
reference to the arms compared, and use more items with fewer repeats.
