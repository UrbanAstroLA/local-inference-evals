# hard-prompt-screen / v2

A screen for non-completion (loops and exhaustion) on one hard question, with independent repeats. It replaces v1
(2026-10-09): v1 sent the same request seed on every repeat, and the engine draws its sampling noise from the seed, so
v1's repeats of a question drew on the same sampler noise. Batching made them vary, but not in a statistically
meaningful way.

**Item:** one GPQA Diamond doc id per run under `gpqa-diamond/v1` prompt rendering (the lm-eval-rendered chat messages;
`lm_eval_prompt_hash` is recorded so the exact prompt can be verified). The question is named in advance, in the
investigation that uses the screen.
**Repeats:** 12 per run. Request seed = 5000 + repeat (5001-5012), the same set in every run, so every repeat is a
separate draw and two runs see the same seeds.
**Sampling:** temperature 1.0, top_p 0.95, max_tokens 327,680, thinking on, streaming.
**Schedule:** 12 concurrent requests (one wave), order fixed by `random.Random(7).shuffle`, freshly started server.
**Early stop and classes:** as v1. From 30,000 reasoning characters, every 10,000 new characters, the zlib compression
ratio of the last 30,000 characters is computed; three consecutive values below 0.10 close the stream (class `loop`).
`ok` = finish reason `stop`; `loop` = stopped early, or finish `length` with tail zlib ratio < 0.15; `exhaust` = finish
`length` with ratio >= 0.15; `error` = transport or server error.
**Primary metric:** failed to finish (loop + exhaust) out of 12. Because a run holds one question and its repeats use
distinct seeds, the summary's 95% Wilson interval (`non_ok_ci95`) applies to that question in that configuration.
Decision rules and any comparison between runs are set per investigation, in advance.
**Validity:** a run needs at least 11 records without error. The server log is checked for KV usage, waiting requests and
preemption, and each run's notes say what it found (a full KV pool means fewer than 12 requests ran at once).

**Fixed-seed control.** A run that repeats a v2 run with seed 1234 on every request, all else identical, is allowed as a
control for the seed itself. Its notes say "fixed-seed control"; it is reported only beside the run it controls, never
as the configuration's failure rate, and `tools/verify.py` rejects repeated seeds in any v2 run not so labelled.

Client: `tools/clients/hard_prompt_screen.py` with `SEED_BASE=5000 CONC=12` (the control: `SEED_BASE` unset).
